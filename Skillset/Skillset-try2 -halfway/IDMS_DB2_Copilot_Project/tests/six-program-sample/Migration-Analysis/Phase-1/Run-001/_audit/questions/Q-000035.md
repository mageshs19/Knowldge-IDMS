## Observed behavior

SQLERROR and SQLERRWS are included but absent. USERABEN is called but not supplied.

Neither converted listing contains an explicit ROLLBACK.

The caller tests SQLCODE again after the restart SELECT helper; a returning error routine could overwrite the first failure.

Targets call SQLERROR on every SQL result other than 0 or the explicitly handled fetch/select +100. OPEN/FETCH failures do not set EOC in those branches. SQLERRWS and SQLERROR are absent; generated IDMS status/control members are absent too.

The main procedures rely on external error routines to stop execution. The implementations were not supplied.

## One business or missing-evidence question

What is the exact failure/non-return contract of SQLERROR, SQLERRWS, generated IDMS status/bind members and USERABEN for the six supplied programs, including preservation of the producing diagnostics and rollback of uncommitted work? Supply the implementation members.

## Why the answer matters

Without this contract, aborted work, subsequent processing, diagnostic ownership and transaction atomicity cannot be proved.

A returning handler can leave the loop active or return with invalid data; missing members block precompile/compile and any claim of equivalent abort/cleanup.

A returning error routine can allow invalid output or continued cursor processing; missing cleanup behavior prevents full equivalence.
