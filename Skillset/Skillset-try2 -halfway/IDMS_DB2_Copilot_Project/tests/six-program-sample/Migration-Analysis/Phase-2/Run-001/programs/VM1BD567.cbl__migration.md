### Source-based analysis and evidence retained

**OBSERVED:** Each record from `OPERATIES` DD010 is moved into a 1200-byte operation layout. The program identifies a form/accounting record using product/service type 1815, client ID, creation date, document ID, operation detail and operation general. The target combines `OBTAIN CALC VMBFAR` followed by `MODIFY VMBFAR` into a searched UPDATE with the six mapped key predicates. A full-record retrieval is unnecessary for the listed business assignment if the predicate uniquely identifies the same row and error/locking behavior is preserved. The parent/child comment `DZSIARTV (PARENT) ---> DZBFARTV(CHILD)` at target L17 is a comment, not a parent validation step. Neither the original direct CALC request nor the target UPDATE executes the supplied subschema's LRF parent path.

Two material changes require separate assessment. The target converts a zero/blank creation date to `00010101` before key formatting, which the original does not do. More significantly, the supplied original `CTR-REC` is initialized to 0 and **never incremented by ordinary reading or processing**. Its advertised 100-record cadence therefore does not occur on a fresh run. The target adds successful-read increments and resets its batch counter after positioning, implementing a plausible intended 100-record protocol but changing observed legacy behavior. This is an observed legacy defect/implementation difference, not evidence that the new behavior has been approved or production-proven.

There are no external business output files. New target final DISPLAYs report cumulative successful reads and successful business UPDATE calls; these have different lifetimes on a resumed invocation. Both programs use a restart row by program/date, but the target adds completed-run rejection and a count-plus-record structure whose UPDATE length actually persists only the count.
