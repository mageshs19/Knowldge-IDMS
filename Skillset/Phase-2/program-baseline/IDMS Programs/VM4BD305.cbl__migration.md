# IDMS Programs/VM4BD305.cbl — IDMS to DB2 Migration Analysis

> **Purpose.** Knowledge base for one program pair: legacy VM4BD305 vs the manual DB2 conversion VMDZ4305. Written for a downstream conversion engine and its reviewers.
>
> **Evidence labels:** `[OBS]` observed in source, `[INF]` inferred, `[UNK]` needs a human answer. **NEW** marks a rule first proposed here (provisional ID `<CAT>-V4305-n`).
>
> **Line references:** legacy = **physical file lines** (`L`). In this file physical line = seq/100 exactly (L176 = 017600 `OBTAIN FIRST VMBTL07-R01`, L215 = 021500, L257 = 025700; verified by search, no inserts). DB2 = cols 1-6 sequence numbers (`seq NNNNNN`; suffixes 00/02/03, jumps after seq 064702 but monotonic). Schema-Listing, VMBTS07, DCLGEN, copybook and mapping-CSV refs are physical lines.
>
> **Pairing.** Legacy header L9-11 "RECHERCHE DES TITRES CONCERNES PAR UNE MUTATION TOTALE / … TOUS LES TITRES ACTIFS EN ENCOURS CHEZ OLD-CI / … ADAPTATION DU VM4OM170" = VMDZ4305 seq 000900-001100 (literal English translation). "TOTAL MUTATION" and "VM4OM170" occur in no other VMDZ program [OBS grep]. Same FDs (DD010 150 / DD100 120), identical WS-IN-REC / WS-OUT-REC / TAB-TOT-MUT / TAB-EVENT, same paragraph names. **Confidence: High.**

## 10. LR semantics

- **SWEEP path** (VMBTS07 L157-164) is a two-level iteration: EACH VMBEFF in AR-VMBEFF1, EACH VMBEVEF in its set. LRF re-enters at the innermost EACH on `OBTAIN NEXT`; after the inner EACH returned `VMBEVEF-EOS`, the next request backs up to EACH VMBEFF [INF LRF re-entry rules; the program relies on it at L215]. DB2 = outer owner cursor + inner member cursor per owner (LRO-V4305-1).
- **Currency.** Members are in the same area (Schema-Listing L1384); LRF keeps the owner position for the area sweep itself (`LR CURRENCY NO RESET`, VMBTS07 L5) — no FIND CURRENT is needed (contrast VM4BD300 direct DML, LRO-V4300-1) [INF] (Q-116).
- **Empty set.** No `IF … IS EMPTY` in the path: the owner is obtained, the inner EACH gets 0307 → `VMBEVEF-EOS` is returned together with a fresh VMBEFF. TRAIT-EFF then skips OB-EVENT and still runs EFF-IN-TAB with DATE-EVENT(1) = 99999999 (no match unless DATE-MUT = 99999999). DB2: zero FETCHes, same EFF-IN-TAB → equal. The VMBEVEF LR area is stale but unused (contrast LRO-Z260-1: here the body is not entered).
- **Stale areas (LRO-N595-1).** Program only reads; no STORE/MODIFY from LR areas → n/a.
- **Order sensitivity** (ORD-V4300-1): slot 1 (0060) and slot 2 (0168) are **last-row-wins** overwrites → order-dependent if > 1 occurrence; ZOEK-CI strict `>` → first row wins on equal transfer dates; the > 25 abend is order-free. Hence DESC changes results only for duplicate 0060/0168 or tied 0092 dates (D-03, Q-110).
- **Chained mutations.** ECRIRE appends a synthetic 0092 (DATE-MUT, NEW-CI) to TAB-EVENT, so mutation I+1 for the same title is evaluated against the new holder (A→B then B→C in file order gives 2 records; reverse order gives 1). Driven by the DD010 file order, identical in both.
- CALL PROCEDURES INFOCOMP/INFODCOM (Schema-Listing L1321-1324, L1385-1388) → ignored (PROC-01).
