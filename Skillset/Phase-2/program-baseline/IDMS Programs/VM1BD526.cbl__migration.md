# IDMS Programs/VM1BD526.cbl — IDMS to DB2 Migration Analysis

> **Purpose of this file.** Knowledge base for one program, written for a downstream AI or Python conversion engine. It records what the legacy program does, how the manual DB2 conversion (VMDZ1526) re-implemented it, and where the two differ.
>
> **Rule IDs** are defined in `../../generic/`. **NEW** marks a rule first seen here.
>

>

## 2. Business purpose and flow

```
VMBEFF   (stock line: product '1002' + stock id 12 + check digit + DB seq)   DZBEFFTV   CALC KY-EFFECT, DUP NOT ALLOWED (Schema-Listing L1319)
   └─ VMBEVEF (product event 0168, good type 0219, NR-ID-GOOD = form key)  DZEVEFTV   VIA VMBEFF-VMBEVEF (L1383)
```

### 2.1 Dispatch (200-VERWERK-INFIL, L147-157)

| `CO-STCIRC-OORD` | Legacy | DB2 |
|---|---|---|
| `'1'` | 210-STORE-EFF (despite the name, it stores only the **event**) | 210-INSERT-EVFF → 211-SELECT-EFF → 260-INSERT-EVEF |
| other | 220-MOD-EVEF | 220-UPD-EVEF → 221-SELECT-EVEF → 222-UPDATE-EVEF |

### 2.2 210-STORE-EFF (L159-194)

```
MOVE SPACES TO VMBEFF, VMBEVEF
EFF key   : CT-RK-TPROD '1002', NR-ID-STOCK-CD ← NR-ST-FORM-AS (9(13)), NS-DB-STOCK ← NS-DB-STOCK-FORM-AS
EFF other : CO-IDPRKB-STOCK, NS-IRMO-STOCK, DA-UBSECIS-STOCK, NR-ID-ISSUE, NR-CD-ISSUE   ← DEAD (see §6)
EVEF      : DA-CR-EVENT-PROD ← PARM date (CCYYMMDD), CT-RK-TEVPR '0168', CT-RK-TGDSV '0219',
            NR-ID-GOOD ← HULP-NR-ID-GOOD (CIO, DA-CREA, ID, OPD, OPG; COMP-3, 20 bytes),
            DB-NR-CI ← NR-CIO-FORM-AS, then NR-CI ← NR-CIO-FORM-AS
STORE VMBTL07-R01 WHERE ST-VMBEVEF
  path: OBTAIN FIRST VMBEFF WHERE CALCKEY EQ KY-EFFECT → 0326 RETURN VMBEFF-NOT-FND; STORE VMBEVEF
  VMBEFF-NOT-FND or LR-ERROR → IDMS-STOP (ROLLBACK + USERABEN)
```

### 2.3 220-MOD-EVEF (L196-227)

```
MOVE SPACES TO VMBEFF; set KY-EFFECT ('1002' + stock + DB seq)
OBTAIN FIRST VMBTL07-R01 WHERE ALL-VMBEVEF-BY-VMBEFF AND CT-RK-TEVPR = '0168' AND CT-RK-TGDSV = '0219'
   path: OBTAIN VMBEFF CALC → VMBEFF-NOT-FND | IF set EMPTY → NO-VMBEVEF-FND | OBTAIN EACH VMBEVEF → NO-MORE-VMBEVEF
   not LR-FOUND → DISPLAY 'RECH EVTS SOUSCRIPTION' + key + status, CALL USERABEN
rebuild NR-ID-GOOD from input
MODIFY VMBTL07-R01 WHERE MO-VMBEVEF        (path: FIND CURRENT VMBEVEF; MODIFY VMBEVEF)
   not LR-FOUND → DISPLAY 'UPDATE CLÉ FORM' + key, CALL USERABEN
```

**Business meaning [INF]:** a '1' input records a destruction/filing event on an existing stock line. A later correction (input ≠ '1') rewrites the form key (NR-ID-GOOD) of the first 0168/0219 event on that stock line.

## 7. Cursor / transaction design

- **No cursor.** Both LR walks become singleton SELECTs:
  - ST-VMBEVEF owner check → `SELECT … FROM DZBEFFTV WHERE <full KY-EFFECT>` (no FETCH FIRST needed: VMBEFF is CALC DUPLICATES NOT ALLOWED, Schema-Listing L1319) [OBS].
  - ALL-VMBEVEF-BY-VMBEFF + predicates → `SELECT NR_ID … WHERE <EFF FK> AND CT_RKTEVPR = '0168' AND CT_RKTGDSV = '0219' ORDER BY NR_ID_479EVEF DESC FETCH FIRST 1 ROW ONLY` (LRO-02).
- **Unit of work:** COMMIT every 100 input records (TELLER) and at EOF. Same as the legacy.
- **Isolation:** not specified (plan default). The legacy ran `USAGE-MODE IS UPDATE` (shared update). No difference for a single batch writer [INF].

| Situation | Legacy | DB2 | Equivalent? |

| Owner VMBEFF missing on '1' | VMBEFF-NOT-FND → IDMS-STOP (DISPLAY, ROLLBACK, USERABEN) | 211 `WHEN OTHER` (includes 100) → 'ERROR AT RECORD NUMBER' + SQLERROR | yes [INF: SQLERROR rolls back and abends, Q-02] |

## 10. LR semantics

| LR keyword | Path (VMBTS07) | DB2 rule | Note |
|---|---|---|---|
| `ST-VMBEVEF` (L182-188 of VMBTS07) | OBTAIN VMBEFF CALC (0326 → VMBEFF-NOT-FND); STORE VMBEVEF | **LRS-11 NEW:** STORE of a VIA member under an existing CALC owner → mandatory owner probe by full CALC key (100 = fatal), then INSERT the member with the owner key as FK columns plus SEQ-01 | Owner probe kept (211). The DB2 version selects 22 BEFF columns that it never uses; an `EXISTS`-style probe is sufficient. |
| `ALL-VMBEVEF-BY-VMBEFF` + WHERE (L124-136) | OBTAIN VMBEFF CALC; IF EMPTY → NO-VMBEVEF-FND; OBTAIN EACH VMBEVEF; 0307 → NO-MORE-VMBEVEF | LRO-02 | All 3 not-found statuses map to SQLCODE 100. |
| `MO-VMBEVEF` (L97-101) | FIND CURRENT VMBEVEF; MODIFY | LRM-01: UPDATE … WHERE NR_ID = :pk from 221 | Only NR-ID-GOOD changes between OBTAIN and MODIFY [OBS L213-218]. SET list is correct. |

**Set order (Q-17).** Legacy "FIRST" = first in VMBEFF-VMBEVEF set order. Schema-Listing L1383-1391 gives LOCATION VIA and pointers NEXT/PRIOR (no OWNER pointer), but not the set ORDER clause. The DB2 version uses `DESC` (newest first). **The same `ORDER BY NR_ID_479EVEF DESC` is used in all 15 VMDZ programs that read DZEVEFTV** (1515, 1526, 1535, 1546 ×2, 1555, 1565, 1575, 1595, 4300, 4302, 4305, 4310, 4420, 7102) [OBS grep]. This team-wide convention implies ORDER FIRST (LIFO) [INF]. The engine should apply DESC consistently and leave Q-17 open for confirmation.

**Record procedures.** VMBEVEF has `CALL PROCEDURES INFOCOMP BEFORE STORE / BEFORE MODIFY, INFODCOM AFTER GET` (Schema-Listing L1386-1389). These are compression exits and have no business effect, so DB2 needs no equivalent [INF]. → **PROC-01 NEW**.

## 12. Restart: FFRECAB variant A (end-of-job update present)

| Aspect | Legacy VM1BD526 | VMDZ1526 |
|---|---|---|
| Key | NM-ID-FF `'VM1BDF526-A'` (extra F typo, as in VM1BD515), DA-CR-FF = PARM date | 'VMDZ1526', phase 1, DA_CR_RS = PARM date `DD.MM.CCYY` |
| Create | not found → STORE at the **first** checkpoint (800 ELSE branch), NB-DAY 15 | INSERT at start (820), NB_DAY 15, LEN 1215 |
| Checkpoint | `TELLER NOT < 100`: 800 (OBTAIN CALC + ADD TELLER + MODIFY) + COMMIT | 830: NB-READ = records read, KY-RESTART = last input, COMMIT |
| End of job | 800 then FINISH (cumulative NS-REC-FF-IN) | 830 with CO_ID_RS '1' |
| Positioning | `UNTIL TELLER NOT < NS-REC-FF-IN`, EOF → STOP01 | `PERFORM NB-READ TIMES 110`, EOF → 120-STOP01 |
| Completed rerun | reads everything, processes nothing, ends normally | abends (V-01) |

D-03: 830 moves 15 to TE-CH-RS-DATA-LEN (INSERT uses 1215), so KY-RESTART is truncated on every checkpoint. There is no functional impact, because positioning uses NB-READ only.

## 15. Reusable rules and open questions

### 15.1 New rules

| Rule | Statement | Guide |
|---|---|---|
| **HLP-09** | Fields moved into an LR element that the path only **OBTAINs** (not STOREs/MODIFYs) are dead: the OBTAIN overwrites them. Drop them in DB2. Check the path in the subschema before mapping any move. | 04, all |
| **LRS-11** | STORE of a VIA member whose path first OBTAINs the CALC owner (`…-NOT-FND` return) → mandatory singleton probe of the owner by full CALC key (100 = fatal, same message as the legacy NOT-FND branch), then INSERT the member with the owner key as FK columns (SEQ-01). | 04 |
| **PROC-01** | IDMS record CALL PROCEDURES (INFOCOMP / INFODCOM compression) have no DB2 equivalent and no business effect. Ignore them, but list them in §10 for completeness. | 04 |
| ORD-01 (convention, from grep) | For DZEVEFTV "first event" lookups, all manual conversions use `ORDER BY NR_ID_479EVEF DESC FETCH FIRST 1 ROW ONLY`. Apply the same until Q-17 is answered. | 03 |
