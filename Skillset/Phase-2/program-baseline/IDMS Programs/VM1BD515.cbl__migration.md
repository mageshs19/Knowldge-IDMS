## 2. Business purpose and flow

**Remarks:** "UPDATE DATABASE INTEKENINGEN OP BCI1 EN BCI2". The program applies **subscriptions on securities issues** ("intekeningen", subscriptions) to the stock structure:

```
VMBWCEF  (issue/stock header: security code + IRMO seq + maturity date)      DZWCEFTV
   └─ VMBEFF   (stock line: product '1002' + stock id 12 + check digit + DB seq)  DZBEFFTV
         └─ VMBEVEF (product event: type '0060', good type '0029', NR-ID-GOOD = form key)  DZEVEFTV
```

### 2.1 Dispatch (VERWERKING, L1790-1800)

| `CO-STCIRC-OORD` | Meaning (comment) | Legacy paragraph | DB2 paragraph |
|---|---|---|---|
| `'1'` | "circulation pas encore mise à jour": circulation is not yet updated | STORE-EFF | 1100-INSERT-EFF |
| anything else | "circulation déjà mise à jour": circulation already updated | MOD-EVEF | 1200-UPDATE-EVEF |

### 2.2 STORE-EFF (L3143-3215)

```
MOVE SPACES to VMBWCEF, VMBEFF, VMBEVEF
WCEF key  : CO-IDPRKB-STOCK ← NR-ID-040SECU, NS-IRMO-STOCK ← NS-SEQ-040IRMO, DA-UBSECIS-STOCK ← DA-UB-FORM-AS
EFF       : same 3 fields (copy of the owner key), NR-ID-ISSUE/NR-CD-ISSUE 0, CT-RK-TPROD '1002', CT-RK-TPROD-EX '1003',
            NR-ID-STOCK-CD ← NR-ST-FORM-AS (13 digits), NS-DB-STOCK ← NS-DB-STOCK-FORM-AS,
            AM-CND / AM-CN / AM-INTER, NX-CPCRE = NX-CPFDU = NS-IDCP, NX-CPAID = NS-IDCP − 1 (if numeric > 0, else 0)
EVEF      : DA-CR-EVENT-PROD ← run date, CT-RK-TEVPR '0060', CT-RK-TGDSV '0029',
            NR-ID-GOOD ← HULP-NR-ID-GOOD (CIO, DA-CREA, ID, OPD, OPG), DB-NR-CI ← NR-CIO-FORM-AS
STORE LR WHERE ST-VMBWCEF-TO-VMBEVEF
  LR-ERROR       → STOP01 + USERABEN
  VMBEFF-EXISTS  → STORE LR WHERE ST-VMBEVEF
                     LR-ERROR or VMBEFF-NOT-FND → STOP02 + USERABEN
```

**Net effect:**
- Ensure the WCEF exists (create it if it does not).
- Ensure the EFF exists. If it already exists, its stored values are **not** refreshed.
- **Always add one EVEF** under that EFF.

### 2.3 MOD-EVEF (L3222-3295)

```
EFF key: '1002' + NR-ST-FORM-AS + NS-DB-STOCK-FORM-AS
OBTAIN FIRST LR WHERE ALL-VMBEVEF-BY-VMBEFF AND CT-RK-TEVPR='0060' AND CT-RK-TGDSV='0029'
  not LR-FOUND → DISPLAY + USERABEN
NR-ID-GOOD ← HULP-NR-ID-GOOD (current form key)
MODIFY LR WHERE MO-VMBEVEF
  not LR-FOUND → DISPLAY + USERABEN
```

**Net effect:** re-link the subscription event of the stock line to the current form key.

### 2.4 Business invariants

| ID | Invariant |
|---|---|
| BIZ-515-01 | CO-STCIRC-OORD = '1' always produces exactly **one new EVEF**. WCEF and EFF are created only if missing. |
| BIZ-515-02 | An existing EFF is never updated by the STORE branch. Its amounts and coupon counters stay as first stored. |
| BIZ-515-03 | NX-CPAID = NS-IDCP − 1, floored at 0 (also 0 when the input is not numeric). |
| BIZ-515-04 | The MOD branch changes **only NR-ID-GOOD** of the **first** EVEF of type 0060/0029 in set order. A missing EFF or event is fatal. |
| BIZ-515-05 | NR-ID-GOOD = CIO(8) + DA-CREA(8) + ID(6) + **OPD(3) + OPG(3)** (in this order, OPD before OPG). |
| BIZ-515-06 | The event date of a new EVEF is the run date (PARM or system date). |

### 4.1 LRS-10 (NEW): store chain with "exists" continuation

The legacy pattern is:

```
STORE LR WHERE <path: find-or-store A; STORE B (1205 → B-EXISTS); STORE C>
IF B-EXISTS → STORE LR WHERE <path: FIND B by CALC; STORE C>
```

The legacy intent is "ensure A, ensure B, always add C". The DB2 form is:

```
SELECT A by PK → 100: INSERT A
INSERT B → 0 or -803: continue      (other → fatal)
INSERT C with FK = B key
```

The second STORE path disappears, because the FK values are already in host variables. Its "B-NOT-FND" branch is unreachable (B was just reported as existing).

**Caveat:** an existing B is **not** refreshed with input values (same as legacy). The engine must **not** convert the `-803` into an UPDATE.

### 4.2 SEQ-01 (NEW): surrogate key for VIA-only member records

VMBEVEF has no CALC key; it is stored VIA its set. The DB2 table therefore gets a surrogate PK (`NR_ID_479EVEF DECIMAL(20)`; CSV L372 says "auto increment seq key"), filled from a **SEQUENCE**, plus `NS_IDMSKEY_479EVEF INTEGER` (the IDMS db-key of migrated rows; 0 for new rows).

Engine rules:
1. For each VIA-only record, look up the surrogate column in the DCLGEN or CSV ("Primary Key" with no legacy field). Use `NEXT VALUE FOR <seq>` in the INSERT, with an explicit column list.
2. The VMDZ1515 form `RIGHT(DIGITS(NEXT VALUE FOR DZEVEFSQ),20)` inserts a CHAR value into a DECIMAL(20) column and relies on an implicit cast. **Prefer plain `NEXT VALUE FOR DZEVEFSQ`** [INF].
3. Set NS_IDMSKEY to 0 on new rows (from INITIALIZE).
4. Set order for members becomes `ORDER BY NR_ID` (ASC for set order LAST/chronological; DESC for FIRST/LIFO). See D-01.

### 5.4 CONFLICT C-01: NR-ID-GOOD format change

| Source | Says |
|---|---|
| Legacy | HULP-NR-ID-GOOD = 4 COMP-3 fields + FILLER XX = 20 bytes (binary packed) moved into NR-ID-GOOD X(20) |
| Mapping CSV L360 | NR-ID-GOOD X(20) → NR_IDGOOD_479EVEF **CHAR(20)** |
| DCLGEN DZEVEFTV | NR_IDGOOD_479EVEF **CHAR(28)** |
| VMDZ1515 | HULP-NR-ID-GOOD redefined as **display** 9(8)+9(8)+9(6)+999+999 = 28 characters |

**Consequences:**
1. The DCLGEN (28) wins over the CSV (20). The CSV row is stale.
2. The **data migration** must unpack the legacy 20-byte packed values into the 28-character display format. Otherwise, the rows migrated from IDMS and the rows written by VMDZ1515 will have different formats in the same column [UNK] (Q-18).
3. **Every other program** that reads or compares NR-ID-GOOD (or redefines it as packed) must use the display layout.

**Engine rule HLP-07 (NEW):**
- When a COMP-3 helper group is moved as a whole into an alphanumeric record field that maps to a CHAR column, check the DCLGEN length.
- If the length equals the **display** length, regenerate the helper as DISPLAY (drop FILLERs), as VMDZ1515 does.
- If the length equals the **packed** length, keep the COMP-3 helper.
- Always raise a cross-program question.

## 7. Cursor lifecycle and transaction flow

**No cursors.** Singleton SELECTs, INSERTs and searched UPDATE by surrogate PK.

```
per record:
  '1': SELECT WCEF → (100: INSERT WCEF) → INSERT BEFF (0 / -803 ok) → INSERT EVEF (seq)
  else: SELECT EVEF id (FK + type predicates, ORDER BY NR_ID DESC, FETCH FIRST) → UPDATE EVEF by id
  WS-TELLER (incremented at read) > 99 → UPDATE DZ01RSTV + COMMIT
EOF: UPDATE DZ01RSTV (CO '1') + COMMIT
```

Unit of work = 100 input records. Each record writes up to 3 rows, so an abend rolls back all rows of the current batch, which are replayed on restart. The data is consistent, because the WCEF/BEFF existence checks absorb replays and only EVEF rows are added once per committed record.

## 10. LR path semantics (VMBTS07 L78-200, LR CURRENCY NO RESET)

| Keyword | Body | Statuses | DB2 |
|---|---|---|---|
| ST-VMBWCEF-TO-VMBEVEF | OBTAIN FIRST WCEF CALC (0326 → DO STORE WCEF END); STORE EFF (1205 → VMBEFF-EXISTS); STORE EVEF | VMBEFF-EXISTS | SELECT/INSERT WCEF; INSERT BEFF (-803 tolerated); INSERT EVEF |
| ST-VMBEVEF | OBTAIN FIRST EFF CALC (0326 → VMBEFF-NOT-FND); STORE EVEF | VMBEFF-NOT-FND | INSERT EVEF (FK from host variables) |
| ALL-VMBEVEF-BY-VMBEFF (+ LR WHERE) | OBTAIN EFF CALC; IF set EMPTY → NO-VMBEVEF-FND; OBTAIN EACH EVEF (0307 → NO-MORE-VMBEVEF) | VMBEFF-NOT-FND, NO-VMBEVEF-FND, NO-MORE-VMBEVEF, LR-FOUND | single SELECT (LRO-02) |

**LR WHERE with constants.** `OBTAIN FIRST … WHERE <keyword> AND <field> = 'lit' AND …` adds the literals as SQL predicates on the member columns. The keyword's walk supplies the FK predicates. This confirms LRO-02.

Other VMBTS07 paths not used here but relevant to other programs:
- ER-VMBWCEF: ERASE ALL MEMBERS, which becomes a cascading DELETE EVEF → BEFF → WCEF.
- ALL-VMBEVEF-BY-VMBWCEF: a 2-level walk.
- SWEEP-VMBEFF-VMBEVEF: an area sweep (EOA/EOS).
- MO-VMBEFF, OB-VMBEFF, OB-VMBFAS, OB-DUP-VMBFAS (OBTAIN EACH by CALC, i.e. duplicates allowed → cursor).

## 12. Restart: FFRECAB variant C

| Aspect | Legacy VM1BD515 | VMDZ1515 |
|---|---|---|
| Key | NM-ID-FF `'VM1BDF515-A'` (typo with an extra F; harmless) | 'VMDZ1515', phase 1, run date |
| Create | at start (STORE when not found), NB-DAY 7 | INSERT at start, NB_DAY 7 |
| Checkpoint | `TELLER > 99`: FIND CURRENT + MODIFY + COMMIT + DISPLAY 'COMMIT' | 800-PROCESS-COMMIT (no DISPLAY) |
| **End of job** | **none**: only `FINISH`. The FFRECAB row keeps the last 100-boundary count. | final checkpoint with CO_ID '1' |
| Positioning | `READ VARYING TELLER … UNTIL SW-EOF OR TELLER > NS-REC-FF-IN` (EOF-safe) | NB-READ TIMES, no EOF guard (D-03) |

**L-01 (legacy defect, informative):**
- The missing end-of-job update means a same-day rerun of a completed job re-processes the tail (< 100 records) and adds duplicate EVEF rows.
- The DB2 version closes this gap.
- **The engine must not reproduce L-01.** Always generate the EOF checkpoint (RST-06).

## 13. Defects and variants

| ID | Severity | Location | Description | Fix |
|---|---|---|---|---|
| D-01 | **Medium (decision needed)** | 1210-SELECT-EVEF seq 078800 | Legacy takes the **first** matching EVEF in VMBEFF-VMBEVEF set order. DB2 takes `ORDER BY NR_ID DESC` (the most recent). ## 15. Reusable rules and open questions

### 15.1 New rules

| Rule | Statement | Guide |
|---|---|---|
| **LRS-10** | Store chain with a `*-EXISTS` continuation becomes probe/insert the owner, INSERT the middle record (0 or -803 → continue), INSERT the leaf. Never turn -803 into an UPDATE. | 04 |
| **SEQ-01** | VIA-only records get a surrogate PK from a SEQUENCE (NEXT VALUE FOR) and NS_IDMSKEY = 0. Member order becomes ORDER BY the surrogate, in the direction of the set order. | 04, 03 |
| **HLP-06** | Group → COMP-3 host variable, or a single legacy field → several columns: use a DISPLAY helper with a REDEFINES split. | all |
| **HLP-07** | A COMP-3 helper group moved into a CHAR column: follow the DCLGEN length (display vs packed) and flag a cross-program format question. | all |
| RST-06 (reinforced) | Always emit the EOF checkpoint, even if the legacy omits it (L-01). | 02 |
