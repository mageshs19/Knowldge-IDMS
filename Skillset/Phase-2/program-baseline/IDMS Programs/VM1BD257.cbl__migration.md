## 2. Business purpose and flow

**Header comment:** "STOCKAGE FORMULAIRES VMBZ : COUPONS : WIJZIGINGEN/MODIFS". The program applies **modifications to coupon forms** that already exist (VMBFC). For each input order line it changes only the settlement status (`NR-ST`) and the DB-status sequence (`NS-DB`).

### 2.1 Per-record logic (TREAT-PROG, L122-160)

```
INITIALIZE LR
move VMBFC CALC key: CIO, ID, DA-CR, OPG, OPD, NS-LINE  (CT-RK stays spaces)
OBTAIN FIRST LR WHERE OB-VMBFC          -- OBTAIN FIRST VMBFC by CALC KY-VMBFC
IF 'VMBFC-NOT-FND' → DISPLAY + USERABEN
move NR-ST-OORD → NR-ST ; NS-DBST-OORD → NS-DB
MODIFY LR WHERE MO-VMBFC                -- FIND CURRENT VMBFC + MODIFY VMBFC
IF 'LR-ERROR' → DISPLAY + USERABEN      (dead code under AUTOSTATUS [INF])
every 100: ADD TELLER TO NS-REC-FF-IN, FIND CURRENT FFRECAB, MODIFY, COMMIT
read next
```

### 2.2 Business invariants

| ID | Invariant |
|---|---|
| BIZ-257-01 | Every input record must match an existing coupon. A missing coupon is **fatal** (both versions). |
| BIZ-257-02 | Only `NR-ST` and `NS-DB` change. All other coupon fields keep the stored values, because the OBTAIN loads them into the LR before the MODIFY. |
| BIZ-257-03 | The key includes DA-CR, so the date conversion must reproduce the value that VMDZ1255 inserted. |

### 4.1 LRM-01-b (NEW): fused OBTAIN + MODIFY

The fused form is allowed when **all** of the following hold:

1. The OBTAIN path is a pure CALC lookup (`OBTAIN FIRST <REC> WHERE CALCKEY = …`) on a record whose CALC key is **unique**: the STORE path returns 1205 → `*-EXISTS`, or the CSV marks all key columns as Primary Key.
2. Between the OBTAIN and the MODIFY, the program does **not read** any field of the obtained record. It only moves new values into it.
3. NOT-FND is fatal in the legacy (or is handled identically to SQLCODE 100).

When all three hold, emit `UPDATE <view> SET <moved fields>, TS_UPDATE, USERID WHERE <all CALC key columns>`, with SQLCODE 100 taking over the NOT-FND branch. Otherwise, use LRM-01 (SELECT first, then UPDATE by PK).

VM1BD257 satisfies 1-3.

**DATE-03 (NEW): key-date symmetry.** When a DATE column is part of the key, the reader/updater program must use **exactly** the same CCYYMMDD → DATE conversion as the program that inserted the row. Otherwise, rows inserted with a special value (0 → 01.01.0001) will never be found.
- VMDZ1255 and VMDZ1257 both map 0/spaces → 01.01.0001 and both lack the 99999999 branch, so they are consistent.
- The engine must generate a **single shared date routine** for all programs.

## 7. Cursor lifecycle and transaction flow

**No cursors.** One searched UPDATE per record. Commit every 100 input records, plus at EOF.

The order of statements in **800-RESTART-CONTROL** matters: `EVALUATE … END-EVALUATE .` is followed by `MOVE 0 TO WS-TELLER` and `SET VMDZ205I-NOT-EOF`. They are still inside the same paragraph and run after positioning, so this is correct.
- Resetting EOF after positioning hides a short-input condition. This is the same issue as D-03.
