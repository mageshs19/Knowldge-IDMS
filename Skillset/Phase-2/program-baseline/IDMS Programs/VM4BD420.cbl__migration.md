# IDMS Programs/VM4BD420.cbl — IDMS to DB2 Migration Analysis

> **Purpose.** Knowledge base for one program pair: legacy VM4BD420 vs the manual DB2 conversion VMDZ4420. Written for a downstream conversion engine and its reviewers.
>
> **Evidence labels:** `[OBS]` observed in source, `[INF]` inferred, `[UNK]` needs a human answer. **NEW** marks a rule first proposed here (provisional ID `<CAT>-V4420-n`).
>
> **Line references:** legacy = **physical file lines** (`L`), taken from a full line listing. The sequence area steps by 10 with inserts (000371-000373, 000641-000643, 002142-002147) and gaps (000590-000600, 002120-002130), so seq is not used (L161 = 001570 `OBTAIN FIRST VMBEFF`, L186 = 001820 `FIND CURRENT`, L201 = 001970 `MOVE '0307'`). DB2 = cols 1-6 sequence numbers (`seq NNNNNN`, non-uniform, file has 499 lines). Schema-Listing, VMBTS07, DCLGEN, copybook and mapping-CSV (`Modified - Field Mapping … V 1.0_Manual.csv`) refs are physical lines.
>
> **Pairing.** Legacy L10 "INFORMATORISCHE KASBON 2." = VMDZ4420 seq 000100 "INFORMATIONAL KASBON 2." (Dutch → English). It is the only hit for that header on either side [OBS grep "KASBON 2|INFORMATIONAL KASBON|INFORMATORISCHE"]. Sub-headers also match: L14 "VERGELIJKING DATABASE EN INVENTARIS" = seq 000140 "COMPARISON DATABASE AND INVENTORY"; L17 "TWEEDE PROGRAMMA" = seq 000170 "SECOND PROGRAM". The FD (DD005, 50 bytes), the UITRECORD, PARAM-DATONLY and the ESDATMAS prologue are also identical. **Confidence: High.**

## 10. LR / DML semantics

- **Area sweep with currency restore.** VMBEVEF is in the same area (Schema-Listing L1384). Each OBTAIN VMBEVEF moves current of area to the event, so `FIND CURRENT VMBEFF` (L186) restores the owner and `OBTAIN NEXT VMBEFF WITHIN AR-VMBEFF1` continues after it [INF IDMS currency]. FIND CURRENT also overwrites the forced or natural 0307 before `PERFORM IDMS-STATUS` (L187), which would otherwise abort. In SQL the outer cursor keeps its position, so FIND CURRENT is dropped (LRO-V4300-1). The unused LR equivalent is SWEEP-VMBEFF-VMBEVEF (VMBTS07.txt L157-164; cf. LRO-Z310-1).
- **Write on natural end of set.** The legacy writes **inside** the walk, after `OBTAIN NEXT` returns 0307 (L211-213). A forced 0307 skips the OBTAIN (L210) and therefore skips the write. DB2 writes **after** the loop when `NOT SW-STATUS-D = 'Y'` and 'C' (seq 009790-010101). This is equivalent because 'D' and 'C' exclude each other at the write point. The outer `IF NOT SW-STATUS-D` is redundant but harmless (DSP-Z250-1 PASS: no merged predicates).
- **Empty set.** OBTAIN FIRST member 0307 → VERWERK never runs → WS-STATUS ' ' → no record. DB2: FETCH 100 → no record. Equal.
- **Order sensitivity** [INF from L192-205]: (a) 'D' (any past 0168 with state ≠ '1') ends the walk with no record → order-free. (b) 'C' needs at least one past 0060 and no 'D' → order-free. (c) 'S' never changes the result: a later 0060 overwrites 'S' and an earlier 'C' blocks 'S' (L-01) → order-free. (d) **UIT-NR-CIO-CRE = NR-ID-GOOD of the last past 0060 in walk order** (unconditional overwrite, L196) → order-dependent when there are 2 or more past 0060 events (D-03, **ORD-V4420-1 NEW**; contrast with ORD-V4300-1 "first-row sentinel").
- **Date filter.** Legacy compares groups (alphanumeric) DA-CR-EVENT-PROD vs PARMDATE. DB2 compares HELP 9(8) vs the group PARMDATE, which is still alphanumeric [OBS COBOL rule: group operand]. Migrated 0001-01-01 → '00000000' ≤ run date, and legacy spaces also ≤ run date (X'40' < X'F0'). 9999-12-31 → '99999999' is excluded in both. Equal (DATE-N130-1 PASS for the compare).
- CALL PROCEDURES INFOCOMP/INFODCOM (Schema-Listing L1321-1324, L1385-1388) are ignored (PROC-01).

## 11. Decommissioned / commented code

### 15.2 New

| Rule | Statement | Guide |
|---|---|---|
| **DML-V4420-1** **NEW** | A program-forced IDMS status (`MOVE '0307' TO ERROR-STATUS`) used to break a set walk becomes an explicit WS switch. Set it where the MOVE was, add it to the `PERFORM … UNTIL` with OR, and reset it before each walk. Actions coded inside the walk on the **natural** end of set (`OBTAIN NEXT` → 0307 → WRITE) move after the loop, guarded by "switch not set" plus the legacy condition. Never test the switch inside the FETCH paragraph. Gate: grep `TO ERROR-STATUS` (hit: VM4BD420 only). | 03, 04 |
| **ERR-V4420-1** **NEW** | `PROTOCOL MODE IS BATCH` (no AUTOSTATUS) programs check status in a **deferred** way (`PERFORM IDMS-STATUS` at the top of the next loop body). Map each check to the DML it actually covers and emit `EVALUATE SQLCODE` right after that SQL statement. Checks after BIND/READY/FIND CURRENT/FINISH have no DB2 statement and are dropped. Do not reproduce the deferral. | 04 |
| **ORD-V4420-1** **NEW** | Extends ORD-V4300-1: an **unconditional overwrite per qualifying member** ("last match wins", e.g. `MOVE NR-ID-GOOD TO WS-…` on every 0060) is order-dependent. The ORDER BY direction must make the last FETCHed row equal the last member in set order. Record a ≥2-match test case. Switches set on "any row" stay order-free. | 04 |
