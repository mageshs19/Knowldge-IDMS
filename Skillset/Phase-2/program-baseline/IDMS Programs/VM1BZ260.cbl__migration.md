## 12. Restart

There is no restart in the legacy program: no FFRECAB, no COMMIT, RETRIEVAL only (L192, L184). DB2 correctly has no DZ01RSTV template, so the team template facts (USERABEN on CO_ID_RS '1', LEN 15/143/1215, NB-READ skip loop, COMMIT every 100, CNT-01) do not apply. A rerun is a full rerun and recreates DD020 (JCL out of scope). Both versions are idempotent for the same input and DB state.

### 15.2 New rules

| Rule | Statement | Guide |
|---|---|---|
| **XPG-Z260-1** | **NEW.** DB2 twins (two conversions that are line-for-line clones, e.g. VMDZ1251/VMDZ1263) must each be diffed against **their own** legacy. A block that is correct for one twin can be wrong for the other when the legacy sources differ in a single status predicate (`= 'LR-FOUND'` vs `NOT = '<OWN>-NOT-FND'`) or in a MOVE source (VMBD205I vs VMBZMEP). The engine generates per-legacy code and never copies twin output. | all |
| **LRO-Z260-1** | **NEW.** A legacy `PERFORM <body> UNTIL 'NO-MORE-<MEM>'` that can be entered with `NO-<MEM>-FND` runs the body once on stale member storage, and its termination depends on LRF NEXT semantics [UNK]. DB2 maps it to a FETCH-driven loop with zero iterations. Do not emulate the stale pass; log it as a legacy defect and a data question. | 04 |
| **MRG-Z260-1** | **NEW.** Balanced-line file merges (`PERFORM READ UNTIL key ≥ …`, AT END high-value sentinel 9999999999999) and key-generation loops (`PERFORM … UNTIL TELLER > 999` with a 9999 terminator) are pure COBOL: copy them verbatim. Keep the DB probe at the same position relative to the merge reads. Never replace a generated-key probe loop by one set-oriented SELECT, because the stop-at-first-missing-coupon semantics would be lost. | 04 |
