# IDMS Programs/VM1BD252.cbl — IDMS to DB2 Migration Analysis

> **Purpose of this file.** This file is a knowledge base for one program, written for a downstream AI or Python conversion engine. It records what the legacy IDMS program does, how the manual DB2 conversion (VMDZ1252) re-implemented each construct, and where that conversion is correct, a variant, or a defect.
>
> Rule IDs are defined in `../../generic/`. Rules first seen in this program are tagged **NEW** and must be merged into the generic guides.
>
> **Evidence labels**
> - `[OBS]` — observed directly in the source.
> - `[INF]` — inferred from consistent evidence.
> - `[UNK]` — requires a human answer.
>
> **Line references.** Legacy references are file line numbers. DB2 references are COBOL sequence numbers (cols 1-6, written `seq NNNNNN`), because the DB2 source contains inserted lines (`006410`, `041510`, …).
>
> **Sister program:** [VM1BD250](VM1BD250.cbl__migration.md). VM1BD250 *stores* the forms; VM1BD252 *modifies* them from the same daily input file (VMBD205I). The restart template, date logic and decommissioned-record list are shared.

## 7. Cursor lifecycle and transaction flow

**Cursors: none.** The legacy OBTAIN FIRST (single row, then MODIFY of the current record) was converted to a **singleton SELECT with `ORDER BY … FETCH FIRST 1 ROW ONLY`**, followed by an UPDATE on the surrogate key.

```
per input record (OPG 53 / OPD 51):
   510  build key in DCLDZBFASTV (INITIALIZE first)
   220  move new values + audit into DCLDZBFASTV
   SELECT NR_ID_479BFAS ... FETCH FIRST 1 ROW ONLY   (replaces OBTAIN FIRST + currency)
     0   -> UPDATE ... WHERE NR_ID_479BFAS = :NR-ID  (replaces FIND CURRENT + MODIFY)
     100 -> fatal
every 100 records: UPDATE DZ01RSTV ; COMMIT
```

- **Why no cursor is needed:** the legacy reads one row and modifies it immediately (`FIND CURRENT` inside the MODIFY path). No iteration takes place.
- **Rule LRM-01 (NEW):** `OBTAIN FIRST <LR> WHERE <calc-path>` followed by `MODIFY <LR> WHERE MODIFY-<REC>` (path `FIND CURRENT <REC>; MODIFY <REC>`) converts to a singleton SELECT of the row identifier, using **the same full key that the CALC path uses**, then `UPDATE … WHERE <pk> = :id`. A searched UPDATE directly on the full key is an acceptable alternative if the key is unique. With duplicates, it would update **all** matching rows, while legacy updates only the first.
- The unit of work and restart are identical to VM1BD250 §7: updates and the checkpoint row are in the same commit scope.

**Rule ERR-02 (NEW) — read-for-update:**
- A "not found" on a mandatory read is a business error. Map it to `WHEN 100 → DISPLAY + SQLERROR`.
- Every UPDATE must test `WHEN 0` only. `+100` on UPDATE (row disappeared) falls into OTHER → fatal.

## 10. LR path semantics

### 10.1 Paths used (VMBTS06)

| Keyword | Path group | Path body (schema line) | Returned statuses |
|---|---|---|---|
| OB-VMBFAS | OBTAIN | `OBTAIN FIRST VMBFAS WHERE CALCKEY EQ KY-VMBFAS OF VMBFAS OF LR` (L275-279) | VMBFAS-NOT-FND (0326) |
| MODIFY-VMBFAS | MODIFY | `FIND CURRENT VMBFAS; MODIFY VMBFAS` (L194-199) | LR-ERROR only |
| ALL-VMBFRT-VMBFORM | OBTAIN | OBTAIN FIRST VMBFORM by CALC (0326 → VMBFORM-NOT-FND); IF VMBFORM-M1 EMPTY → NO-VMBFRT-FND; OBTAIN EACH VMBFRT WITHIN VMBFORM-M1 (0307 → NO-MORE-VMBFRT) (L300-311) | VMBFORM-NOT-FND, NO-VMBFRT-FND, NO-MORE-VMBFRT |
| ALL-VMBFRV-VMBFORM | OBTAIN | same shape for VMBFRV (L326-337) | VMBFORM-NOT-FND, NO-VMBFRV-FND, NO-MORE-VMBFRV |
| ALL-VMBFTEL-VMBFORM | OBTAIN | FORM by CALC → EACH VMBFTE WITHIN VMBFORM-M1 → EACH VMBFTEL WITHIN VMBFTE-VMBFTEL (L358+; 2-level walk) | VMBFORM-NOT-FND, NO-VMBFTE-FND, NO-MORE-VMBFTE, NO-VMBFTEL-FND, NO-MORE-VMBFTEL |
| MODIFY-VMBFRT / FTEL / FRV | MODIFY | FIND CURRENT + MODIFY | LR-ERROR |

### 10.2 Legacy code-level status mistakes (informational)

- **250 tests `'VMBFRT-NOT-FND'`, but the path returns `NO-VMBFRT-FND`.**
  - If the form has no FRT member, the status is NO-VMBFRT-FND. That status is not tested, so the program continues to MODIFY-VMBFRT with **no current VMBFRT**. The result is LR-ERROR, then IDMS-STOP.
  - The net effect is the same (abend), but via a different route.
  - Engine: treat every non-LR-FOUND status on a mandatory read as fatal.
- **290 tests the statuses correctly.** The path returns VMBFRV records only on LR-FOUND; NO-MORE-VMBFRV in 295 is fatal (the order was not found).
- **295 loop:**
  - `PERFORM 295 UNTIL AM-CNS-GDIFRV = AM-CNS-FORM-AS AND NR-ST-GDIFRV = NR-ST-FORM-AS` is a test-before loop.
  - If the first FRV matches, no NEXT is issued (correct).
  - This is **program-side filtering** of an LR walk.
- **270 / 275:**
  - The LR WHERE has field predicates (`AND NS-RK-GDIFTEL = … AND CT-LINE-GDIFTEL = …`), so LRF filters inside the path.
  - The program must still loop on `NO-VMBFTEL-FND` / `NO-MORE-VMBFTEL`, which are returned per FTE when an FTE has no matching FTEL.
  - The loop ends at LR-FOUND, and `NO-MORE-VMBFTE` is fatal.

### 10.3 Conversion patterns for LR walks (for reinstated or other programs)

| Legacy pattern | DB2 pattern | Rule |
|---|---|---|
| OBTAIN FIRST via CALC key, then MODIFY current | singleton SELECT of PK by **full CALC key** + `FETCH FIRST 1 ROW ONLY`, then UPDATE by PK | LRM-01 |
| OBTAIN FIRST/NEXT over `owner → EACH member` + **LR WHERE field predicates**, stop at first LR-FOUND | **one** singleton SELECT that joins owner key (as FK columns on the member) and the predicates in WHERE, `ORDER BY <set order>` `FETCH FIRST 1 ROW ONLY`; 100 → fatal | **LRO-02 NEW** |
| OBTAIN FIRST/NEXT over owner → EACH member + **program-side** filter loop until match | same as LRO-02: move the program-side condition into SQL WHERE. Keep the "first matching in set order" semantics with ORDER BY. | LRO-02 |
| 2-level walk (FORM → FTE → FTEL) | join or FK chain: FTEL carries FTE FK, FTE carries FORM FK → `WHERE <FORM FK cols> AND <FTEL predicates>` (needs FK columns on both children) | LRO-02 |

**Set order matters.** For "first match" semantics, the ORDER BY must reproduce the IDMS set order (insertion order: NEXT / LAST, or sorted). With a sequence surrogate key, `ORDER BY NR_ID ASC` reproduces insertion order (VMDZ1252 uses this) [INF].

**Resolved (Q-12 / Q-13, user answer + `workspace/Schema-Listing.txt`):**
- DB2 tables carry **two composite keys**: the IDMS CALC key columns *and* a surrogate `NR_ID_xxx` added as an extra primary key [OBS user].
- The set order and duplicates option vary per record and per set. Look them up in `Schema-Listing.txt` [OBS user].
- VMBFAS: `LOCATION MODE CALC USING KY-VMBFAS DUPLICATES LAST` (Schema-Listing L415; sort control `ASC DUP LAST`, L428) [OBS]. In IDMS, BFAS rows *can* share a CALC key. A new duplicate is stored after the existing ones, and `OBTAIN CALC` returns the **oldest** one.
- DB2 equivalent: `WHERE <full CALC key> ORDER BY NR_ID_479BFAS ASC FETCH FIRST 1 ROW ONLY`, assuming NR_ID ascends in insertion order. **The ORDER BY must stay in LRO-01.** D-01 still stands, because the WHERE clause must use the full CALC key.

## 11. Decommissioned records

This program confirms LRS-09 for **MODIFY**:
- All three dropped paragraphs (250 / 270 / 290) only *read* VMBFORM (as an owner for navigation) and *modify* a decommissioned record (VMBFRT / VMBFTEL / VMBFRV).
- The DB2 version therefore removes the **WHEN entries themselves**. The OPD values 65 / 71 / 41 now fall through as "unknown" (skipped and counted).

**Rule extension LRS-09-b (NEW):** if, after dropping decommissioned records, a dispatch branch has no remaining DB2 effect, remove the WHEN. The owner existence check (for example VMBFORM-NOT-FND) is lost. Record this as a behaviour change (V-02), not as a defect.

## 12. Restart

The program uses the same FFRECAB → DZ01RSTV template as VM1BD250 §12, with the following differences in the DB2 version:

| Aspect | VMDZ1250 | VMDZ1252 |
|---|---|---|
| Paragraph names | 800-PROCESS-COMMIT, 810/820 | 800-RESTART-CONTROL, 810-JOB-IS-RESTART, 820-WRITE-RESTART-REC, **830-PROCESS-COMMIT**, 840-GET-TIMESTAMP, 850-CALL-USERABEN |
| QUERYNO select / update | 907 / 989 | 520 / 539 |
| TELLER reset | in 200 after commit | inside 830 |
| WS-INPUT-KASBONS | only set during positioning (stale) | set after every read (consistent) |
| PROGRAM-NAME | not set | set from CS-PROGRAM |
| Legacy key | 'VM1BD250-A' | 'VM1BD252-A' → 'VMDZ1252' phase 1 |

**Engine rule:** paragraph names and QUERYNO values are **not standardized** across manual conversions. The engine should pick one template (recommended: the VMDZ1252 layout plus the VMDZ1250 99999999 date branch) and apply it uniformly. QUERYNO should be unique per program.
