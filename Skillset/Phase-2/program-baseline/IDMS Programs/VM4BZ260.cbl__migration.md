# IDMS Programs/VM4BZ260.cbl — IDMS to DB2 Migration Analysis

> **Purpose.** Knowledge base for one program pair: legacy VM4BZ260 vs the manual DB2 conversion VMDZ4260. Written for a downstream conversion engine and its reviewers. First pair with a business **ERASE** (IDMS) → **DELETE** (DB2).
>
> **Evidence labels:** `[OBS]` observed in source, `[INF]` inferred, `[UNK]` needs a human answer. **NEW** marks a rule first proposed here (provisional ID `<CAT>-W4260-n`).
>
> **Line references:** legacy = **physical file lines** (`L`), verified with Select-String. Header seqs 000120/000130 are duplicated (L13-17) and seqs 000380-000400 are missing, so seq ≠ line in the header/FD; from L42 on, line = seq/10 + 1 (e.g. seq 002140 `ERASE VMBFC` = L215, seq 002300 `COMMIT` = L231). DB2 = `seq NNNNNN` (cols 1-6 of VMDZ4260, 490 physical lines). Schema-Listing, VMBTS09, DCLGEN and CSV refs are physical lines.
>
> **Pairing.** Legacy L8-9 "ARCHIVAGE D.B. FORMULAIRES C : ERASE DES FORM C ARCHIVES (PAR CI/DI)" = VMDZ4260 seq 001100-001200 "D.B. ARCHIVING FORMS C: DELETION OF ARCHIVED FORMS C (PAR CI/DI)" (exact translation, "(PAR CI/DI)" kept verbatim). The pair also shares FD FCARCH DD010 35 bytes, the REC-FCARCH layout incl. FC-DBKEY, PARAM-DATONLY and the D-PROG / TRAIT / READ-FCARCH / F-PROG skeleton. Number rule holds (BZ260 → 4260; VMDZ1263 = VM1BZ260). **Confidence: High.**

## 9. OCCURS / REDEFINES

No OCCURS, no WS REDEFINES in legacy. FC-KEY-VMBFC is a positional image of KY-VMBFC with FILLERs for the parts the program never names (L65-71 vs Schema-Listing L1212-1222); the 27-byte group compare (L202) and group MOVE (L258) treat it as one alphanumeric key. DB2 adds only DA-CCYYMMDD-R (seq 007900). `MOVE ZEROES TO DA-CCYYMMDD` (seq 019000) and `MOVE ZEROES TO WS-DATE` (seq 020510) never touch the '.' markers → DATE-Z310-1 PASS. FD 35 vs REC-FCARCH 40: bytes 36-40 are spaces after READ INTO (L-03).

## 10. LR / DML semantics (ERASE)

| Element | Legacy | DB2 |
|---|---|---|
| Verb | `ERASE VMBFC` — **plain ERASE** (no PERMANENT/SELECTIVE/ALL) (L215) | `DELETE FROM DZMBFCTV WHERE 3 cols` (seq 041200-041600) |

| Effect as member | disconnected from VMBSIC-VMBFC (NEXT/PRIOR relinked; no OWNER ptr) and removed from CALC chain | child row deleted; parent DZBSICTV untouched, RI never violated |
| Owner | VMBSIC deliberately kept (L13-15). LR path ER-VMBSIC = `ERASE VMBSIC ALL MEMBERS` (VMBTS09 L110-115) exists but is not used | DZBSICTV kept. No purge of empty VMBSIC/DZBSICTV in workspace (VM9BD900-902 / VMDZ9900-9902 purge SIAS/SIAR/BSIR/SIDN only) [OBS] (Q-141) |

### 15.2 New

| Rule | Statement | Guide |
|---|---|---|
| **DML-W4260-1** **NEW** | Direct-DML ERASE walk (`ERASE <rec>` + `OBTAIN NEXT/PRIOR <rec> WITHIN <set>` UNTIL end-of-set OR group fields change) on a record that owns **no** set (Schema-Listing DBKEY positions without OWNER rows) → one searched `DELETE FROM <view> WHERE <group columns>`; 0 → count `SQLERRD(3)`; +100 → legacy not-found branch (keep its severity: DISPLAY+continue here); OTHER → SQLERROR. No cursor, no WITH HOLD, no `DELETE WHERE CURRENT OF`, no probe SELECT. If the record owns sets: plain ERASE → check children first (0230 parity), ERASE PERMANENT/ALL → child-first DELETEs unless ON DELETE CASCADE (LRS-08). | 04 |

Contiguity in set order is not expressible → raise a data question (D-01). | 04 |
| **DML-W4260-2** **NEW** | `OBTAIN <rec> DB-KEY <file field>` + key verify + CALC fallback + owner-walk fallback, all ending in the same predicate → one key-based SQL; drop the DB-KEY tier (not portable), keep the file field in the layout; merge the not-found messages only when the legacy treats them alike. | 04 |
| **RST-W4260-1** **NEW** | Legacy checkpoint `count − 1` (commit inside a multi-ERASE loop, in-flight record partially done) becomes the template full count when DB2 makes the per-record work one statement and commits only between records; record PASS. Requires idempotent per-record work (DELETE is), which also makes system-date midnight restarts harmless. | 02 |
